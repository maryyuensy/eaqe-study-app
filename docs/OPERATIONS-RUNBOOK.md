# 地產牌研究所：營運與故障處理手冊

版本日期：2026-10-04。適用於目前第一版程式及尚未啟用的外部服務；本文件沒有執行公開部署、真實收款、刪除帳戶或修改服務設定。✅ 表示本機已有對應程式／證據；⭕️ 表示待實作、外部驗收或營運者確認。不能以本文件代替 CP0–CP8 上線驗收。

## 2. 每宗問題最少記錄

- 接報時間及發生時間，列明香港時間、網站版本／網域、手機或電腦、瀏覽器及操作種類。
- 影響範圍：一位使用者、一部裝置、多個帳戶，或整個服務；是否仍有待同步事件。
- API 路徑、HTTP 狀態、錯誤碼及 request ID；只記路徑，不抄錄含 token 的完整網址。
- 同步問題可記該使用者自己的 event ID／session ID；題目問題只記穩定題目 ID、版本、錯誤摘要及官方核對連結。
- 執行人、處理原因、已採取的動作、驗證結果及尚未完成事項。這是所需紀錄格式，目前沒有完整客服管理介面或自動操作稽核系統。

身份核對及紀錄保存的正式程序、客服聯絡方式與負責人仍待設定；不要把未驗證的來訊當作另一帳戶的查詢／刪除授權。沒有訂單系統時，不能承諾已可查本人訂單。

### 安全取得 request ID

1. 電腦可在瀏覽器開發者工具的 Network 選取失敗的 `/api/…` 請求。
2. 只複製 **Response Headers 的 `X-Request-ID`**，或錯誤回應 JSON 的 `requestId`；另記狀態及 `error.code`。
3. 不複製 Request Headers、Cookie、Authorization、Request Payload、整份 HAR 或「Copy as cURL」。登入及刪除 payload 含密碼；驗證／重設回呼含單次 token。
4. `ApiClient` 保留合法 UUID 格式的伺服器 request ID；既有錯誤提示及待同步錯誤在收到有效 ID 時顯示「參考碼」。可直接複製這個參考碼；缺少或非法 ID 不顯示，也不代表操作沒有失敗。手機沒有參考碼時，可先記發生時間、頁面及錯誤文字，由授權營運者查最少必要的後端紀錄；不得因此要求提供登入資料。

API 預設只記錄 5xx；4xx 及成功操作沒有完整追蹤日誌。平台自動產生的日誌是否另外包含敏感資料，仍須在 staging 檢查。

### 不可索取或公開的資料

不得要求使用者提供密碼、JWT、access／refresh Cookie、重設連結、驗證 token、Supabase secret／service-role key、Stripe secret 或 Webhook secret。不要把上述資料放入 GitHub issue、聊天、畫面截圖或程式碼。不要要求整份帳戶匯出作常規診斷；匯出含個人作答及使用資料，只有明確需要且經授權時才在私人渠道取最小範圍。

`service-role`／secret key 只可留在受控私人後端或受控管理作業的秘密設定中；不能交給瀏覽器、題庫 JSON、客服使用者或公開部署資產。一般學習操作使用已驗證使用者身分；客服不得用 service role 直接替使用者修改分數、掌握狀態或付費權限。

## 3. 常見問題診斷

### A. 收不到驗證信／忘記密碼電郵

1. 先確認環境及 `/api/config`。`authEnabled:false` 或 503 可能是正式登入尚未啟用，不代表使用者密碼錯誤。
2. 檢查所填電郵及垃圾郵件；註冊、forgot、resend 的一般訊息不代表帳戶必定存在，也不代表郵件已實際送達。
3. 429 時停止反覆送出；依 `Retry-After` 等候，仍受該操作的較長限流時段及 provider 限制約束，不可保證 60 秒後必定成功。
4. 授權管理者在 **測試環境** 核對 Auth email confirmation、寄件身分／SMTP、寄信配額、provider 錯誤及 DNS 驗證；日誌不得抄出 token 或完整信件連結。
5. 核對 Site URL、redirect allowlist 及範本的 token-hash 回呼；不要設萬用 redirect 或把驗證連結導至不受控網域。
6. 以實際 Gmail／Outlook／手機收信驗收，包含不同裝置開信及郵件安全掃描。現有回呼可能被會執行 JavaScript 的掃描器預先消耗；尚無「所有掃描器均不會消耗連結」的保證。

### B. 密碼重設失敗／連結已使用

1. 核對是否從最新 recovery 電郵進入，而非普通登入 token。不要手動改 Cookie 或要求使用者把重設連結轉交客服。
2. Recovery 證明只有十分鐘、綁定使用者且只能消耗一次；401 可表示過期、缺少證明或已使用，應重新申請連結。
3. 本程式在更新 provider 密碼 **之前** 消耗 nonce；若 provider 更新失敗，舊證明亦不能再用。記 request ID，確認服務狀態後重新取得連結，不能宣稱可原樣重跑成功。
4. 密碼更新成功但 `sessionsRevoked:false` 時，畫面會提示其他會話未全部撤銷；不能把「密碼已改」當作所有舊會話均失效。授權管理者須查真實 provider 撤銷結果。
5. 真實 Supabase 的直接 Auth 密碼更新及 secure password change 設定須另行驗收；自訂網站 API 的限制不代表 provider 所有入口自動受到同一限制。

### C. 作答已完成，但紀錄未同步

1. 保留原瀏覽器及待同步資料；先確認網絡、登入帳戶、待同步數及錯誤文字。不要先清除 localStorage、退出後刪資料或重新安裝瀏覽器。
2. 訪客紀錄只在原瀏覽器；訪客沒有雲端同步。登入帳戶與訪客紀錄分開，舊公開版遷移尚未完成，不可承諾登入後自動搬移。
3. 401：以同一帳戶重新登入後重試。409 `account_mismatch`：停止該分頁的同步，先辨認當前 Cookie 帳戶；不要改 event owner 或把 A 的事件重新送到 B。
4. 一般 409 conflict：讀取最新 session／設定版本再處理；不得用另一 event ID 重送舊答案，以避開版本或冪等檢查。
5. 400／403／404／413／415／422 目前會保留為不可自動重試事件；檢查存取期限、被撤回的題目版本、session 所屬帳戶及欄位格式。人工判斷後修復原因，不能只按無限重試。
6. 網絡、429 或 5xx 會保留原事件，有限次數重試；人工重試仍須保留 **同一 event ID 及同一內容**。伺服器已接受但回應遺失時，原事件重送應回原結果。
7. 比對同一帳戶第二裝置的同步結果及事件數；本機已測過 HTTP→API→PostgreSQL 不重複計數，但真實 PostgREST／兩部裝置仍待驗收。

### D. 看見另一帳戶資料／跨分頁切換帳戶

1. 立即停止受影響分頁的提交及同步，記最小必要證據。不要為了重現而讀取、匯出或傳送另一帳戶完整資料。
2. 由 `GET /api/account` 辨認目前經 Cookie 驗證的帳戶，與該分頁綁定帳戶／outbox owner 比較。`X-App-Account` 只是防止錯帳戶寫入，不能授權存取指定帳戶。
3. 預期不一致時，API 回 409 `account_mismatch`，原事件暫停並保留；重新登入原帳戶後才可同步。B 不應讀寫 A 的 session。
4. 若實際出現跨帳戶資料而非單純錯誤提示，視為需優先處理的隔離問題：暫停受影響入口、保全不含 token 的證據、由授權管理者查權限及會話。不得自行把 body 中的 user ID 改成「正確使用者」。
5. `AUTH_ENABLED=false` 只停止本應用的相關入口；它不是全面撤銷 Supabase 會話或直接 Data API 的開關。需要全面限制時，須由授權管理者按已驗證的 provider／gateway 程序處理；目前尚未演練正式事故停用。

### E. 題目答案／解說疑似錯誤

1. 收集題目 ID、版本、出現頁面、錯誤摘要及使用者所指概念；不公開複製完整書本題幹或私人教材來源。
2. 查 [題庫覆核報告](QUESTION-CONTENT-REVIEW.md) 及阻擋清單，避免把已知待覆核題誤報成新問題。以 EAA／政府現行資料核對，記官方連結及核實日期。
3. 有答案或必要事實矛盾時，由授權開發者將該版本停用／加入阻擋並更新 review policy；不以「暫時當答案正確」繼續評分。商用發布另外須通過使用權與人工核准。
4. 經核准的內容修正使用新版本；既有歷史作答保留原題目版本及原評分，不直接改寫使用者舊紀錄。本輪匯入器只支援完整獨立題，不可把有共同題幹的個案拆成不完整獨立題。
5. 改人名、詞句或題目次序不能保證商業使用權；不得以降低相似度為處理目標。現有候選草稿仍為 draft，不得由客服或自動流程直接發布。

### F. 帳戶刪除中途失敗

1. 客服不可代收密碼；使用者須在網站自己完成同帳戶重新驗證及 `DELETE` 確認。
2. 409 可能是金融資料 gate：含 access grant 的帳戶目前不自動刪除。金融保留、退款及有效權限處理仍待政策，不能改 SQL 或清掉 grant 以繞過。
3. 刪除流程先把 profile 掛起，再呼叫 Auth 刪除。若後者失敗，可能出現「Auth 使用者仍存在，但學習操作被停止」的中間狀態。
4. 由授權管理者只讀核對 request ID、Auth 使用者是否仍存在、profile 狀態及金融 gate；不得收集密碼或以來訊自報 UUID 直接執行管理刪除。
5. 目前沒有持久工作、tombstone、完成狀態或客服重跑端點。SQL 刪除準備可容許同帳戶重試，**不等於整段 API／備份清理可安全自動重跑**。完成刪除或恢復掛起須先確定真實 provider 狀態，再按授權處理方案執行及記錄。
6. 本機 cascade 測試不表示備份亦已清除。還原資料後避免復活已刪帳戶的流程尚未完成；不能向使用者承諾「所有備份已永久刪除」。

## 4. 停止收款、故障回退及恢復

### 目前狀態

收款關閉，沒有真實 Checkout／Webhook／訂單 API，也沒有客服退款或對帳工具。`PAYMENTS_MODE=test` 只是容許的設定值，不表示付款流程已實作。不能以手動補付費 flag 或 service-role 寫 grant，代替驗證付款。

### 正式付款功能完成前需補齊

- 分開「停止建立新 Checkout」與「繼續接收已產生付款的 Webhook」；停收新單不得丟棄既有付款通知。
- Webhook 簽章驗證、唯一 provider event ID、重複及亂序通知、授權交易、退款／爭議狀態與持久重試。
- 私人訂單查詢、provider 與本地授權對帳、受權管理員的重跑／退款流程及操作稽核。
- 實際付款失敗的責任人、告警收件及應答程序；退款條件、延期／改期及資料保留政策仍須由營運者確認。

上述接口沒有完成時，不能指示客服使用不存在的「重跑 Webhook」按鈕，也不能把真實付款當作可反覆試驗的普通測試。

### 網站回退程序（待 staging 演練）

1. 記錄目前 Git commit、題庫核准版本、三份 migration、環境與 flag 差異，以及上一份可驗證且相容的發布產物。
2. 驗證備份、部署及 DB 版本相容性；只回退到不含未核准題庫的受控產物，不能把舊 `dist/` 的完整原型題庫當作安全回退。
3. 前端回退不會回退資料庫或恢復資料；沒有通用 migration down 程序。不得刪 schema、覆蓋正式 DB 或直接把正式資料還原至舊結構。
4. 本機備份 smoke test 是一次性測試資料庫的 dump／restore，不涵蓋真實 Supabase、金融事件、tombstone 或完整 T30。正式恢復必須另設測試環境並驗證刪除／付款語義。
5. 驗證健康、登入、隔離、原 session／作答與同步後才解除暫停；保留事前／事後證據。不以頁面能打開當作恢復完成。

## 5. Git 與舊部署的完整題庫風險

原型 `dist/questions.json` 仍有完整 484 題；原始免費標記 20 題，已知問題阻擋後訪客原型可用 467 題（SQE 428 題）／免費 19 題。這些計數不代表商業核准，目前商業核准為 0。公開 Git、歷史提交或舊 Vercel 產物中可能仍保留完整原型題庫；新 API／新構建不能撤回已下載的副本。

新商用構建以明確資產白名單及人工核准輸出，只公開核准免費題，付費題留在私人後端。預設無核准題時阻擋構建；明確 `--allow-empty-preview` 只建立空題庫及提示，不能當成已完成商用題庫。`vercel.json` 與 `vercel.commercial.json` 均已改用 `node scripts/build-commercial.mjs`／`release/site`，防止下一次一般 Git 部署重新輸出未審核 `dist`。本輪沒有部署或下架現有版本；構建失敗也不會自行移除上一份線上部署。Vercel 專案設定覆寫及 CLI 的 `.vercelignore`／完整構建輸入仍須實際驗收。

### ⭕️ 待授權盤點及處理

- GitHub 目前分支、歷史提交、release／附件，以及是否公開、可下載及可 fork；以清單記錄路徑／版本，不公開轉貼題幹。
- 舊 Vercel production／preview deployment、alias 及檔案存取；新網域不能自動移除舊產物。
- 建立可用內容依據及替代題庫後，決定停用／移除舊公開產物、儲存庫可見性及是否需歷史清理。Git 歷史重寫與外部移除涉及其他使用者及不可恢復影響，本手冊沒有執行或授權這些操作。
- 檢查未核准題、私人教材來源及建立者個人紀錄是否留在公開資產；不要將私人 `study/` 或 draft 批次加入部署。
- 如實際發現外洩秘密，再由授權持有人撤銷／輪替；本輪沒有證據可宣稱已發生憑證外洩。

相應使用權判斷與不能保證零訴訟風險的說明見 [題庫覆核報告](QUESTION-CONTENT-REVIEW.md)。不能靠改名、調序或把原始檔藏到另一分支解決已公開內容的商業使用權。

| 兩部真實裝置的測試者 | A／B 兩個測試帳戶；只用另行核准的合成題或已核准題 | 手機作答→電腦同步、離線重送不重複、設定衝突、跨分頁 Cookie 切換、錯題清除／不確定再加入 |
| Voyce／商戶及營運者 | 付款供應商與測試帳戶、試行方案適用範圍、退款／爭議／改期政策；之後才安排正式收款授權 | 測試 Checkout、Webhook、到期、退款／爭議與對帳均通過，非只有一次付款成功 |
| 營運負責人 | 故障收件、必要日誌保存、操作稽核及處理人 | 告警實際送達；恢復／回退、刪除中斷與付款事件重跑有可驗證記錄 |

測試專案不能執行 `db/tests/bootstrap.sql`：該檔只建立本機合成 Auth schema。真正 staging 依 [後端設定指南](BACKEND-SETUP.md) 安裝三份正式 migration，以受控方式設定環境及測試。正式服務未確認前，保持 Auth／收款未啟用，不把本機合成測試結果寫成「正式登入已完成」。
