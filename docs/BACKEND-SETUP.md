## 本機操作

使用 Node.js 24，從專案根目錄執行：

```bash
npm ci --ignore-scripts
cp .env.example .env.local
node --env-file=.env.local scripts/check-environment.mjs
npm run test:ci
npm run dev
```

未接入服務時，檢查會顯示「尚未設定」。它允許繼續測試原型；需要接入帳戶／資料庫前，必須明確要求對應欄位：

```bash
node --env-file=.env.local scripts/check-environment.mjs --require=auth,database
```

不要把真實金鑰寫進範本、題庫、前端或對話。本機只填 `.env.local`；遠端使用部署平台環境變數管理。`.env.example` 中的 Supabase／Stripe 是清單候選設定，尚未建立或連接帳戶。

檢查目前能識別設定不完整、遠端 HTTP、明示跨環境資料設定、部分公開秘密格式及真實付款金鑰。它不能證明兩組連線實際指向不同資料庫，不能證明憑證有效，也不能代替專案權限及部署資產核查。

## 外部接入順序 ⭕️

1. **確認服務專案存取權。** 在具權限的 Vercel 專案檢查設定與部署紀錄；選定帳戶及資料庫服務後，建立獨立測試資料專案。正式資料不得用於預覽。
2. **填入測試設定。** `APP_ENV` 與平台環境一致；`APP_BASE_URL` 使用實際 HTTPS origin；`DATA_ENV` 指定相同環境。完成結構檢查後，實測連線與專案識別。
3. **接入身份驗證器。** 驗證 token 簽署、發行者、受眾、有效期及帳戶狀態；核實後回傳 `{id}`。測試有效、偽造、過期及已撤銷憑證；完成前不開放私人資料端點。目前採 Bearer 接口作開發準備，瀏覽器憑證保存、刷新及 XSS 防護仍待 CP2；如改用 Cookie，另加 CSRF 防護。
4. **建立及驗證 migrations／RLS。** 用空白資料庫重建，使用兩個測試帳戶檢查隔離，保留恢復測試證據。題庫匯入分開執行；原建立者的私人作答及錯題不遷移。
5. **補上共享限流。** 身份及輸入檢查後，按帳戶／操作限制請求；不能依賴單一函式實例的記憶體計數。檢查錯誤回覆、平台日誌及輸入長度。
6. **設定寄信及回呼。** 取得寄信服務／網域權限，核實 DNS、允許的回呼 origin、電郵連結及送達。僅為實際接入的服務更新 CSP。
7. **驗證預覽。** 檢查 `/api/health` GET／HEAD／405、靜態介面、秘密檔案未公開及非測試人員的存取限制；存活檢查通過後仍需登入、RLS 及寄信驗收。
8. **加入發布門檻。** 將 CI 設為必須通過的分支檢查；確認預覽／正式發布設定與版本標記。CI 不包含付款、雲端同步或真機驗收。

Vercel 文件參考：[Node.js Functions](https://vercel.com/docs/functions/runtimes/node-js)、[Node.js runtime 版本](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)（2026-10-03 核查）。函式採 Web `Request`／`Response` 接口；實際專案部署仍待驗證。

| --- | --- |
| 服務接入 | 專案存取權、寄信／網域管理方式；經營者與商戶核身由本人完成。 |
| AI 接入 | 供應商／模型、總體與每帳戶成本上限、免費／付費用量、對話是否保存及期限。 |

| 公開收費 | 題庫答案及使用權覆核、商戶資料、客服信箱、正式網域、真實試用者及服務預算。 |
